# Zvonocheg — дизайн продукта и архитектура

## Продукт

Закрытое пространство для 10–20 друзей. Веб и Windows на первом релизе, мобильный клиент позже. Первый контрольный сценарий — два человека из разных сетей входят по приглашениям, обмениваются зашифрованными сообщениями и разговаривают в голосовой комнате. Сначала веб ↔ веб, затем веб ↔ Windows.

| Экран | Поведение |
|---|---|
| Приглашение и вход | Одноразовое приглашение открывает регистрацию по логину и паролю. Повторный вход по логину и паролю восстанавливает доступную историю без подтверждения другим устройством. |
| Пространство | Слева общие чаты, голосовые комнаты с участниками и личные диалоги. В центре активный чат или звонок. |
| Личные сообщения | Текст, фото, счётчик непрочитанного, разделитель непрочитанного, статус «прочитано» у своих сообщений, кнопка звонка и записи о пропущенных вызовах. |
| Общий чат | Текст, фото, собственные счётчик и отметка последнего прочтения. |
| Голосовая комната | Вход без вызова остальных, список участников, микрофон, камера, демонстрация и выход. Видно, когда идёт захват и включён звук приложения. |
| Администрирование | Роль admin выдаёт и отзывает приглашения, управляет участниками и ролями, создаёт и удаляет общие чаты и комнаты. User участвует в чатах и звонках. Личные диалоги доступны обеим ролям. |

Начальные допущения — общие комнаты доступны всем активным участникам, закрытые комнаты отложены, новые участники видят общие сообщения с момента вступления. Права проверяются сервером. Защищаем последнего администратора от случайного удаления или понижения роли.

## Техническая схема

Предлагаемый стек — TypeScript и React, общий UI и клиентские модули для браузера и Electron. Windows-клиент поставляет локальную сборку UI и использует ограниченный IPC для уведомлений и системного захвата. Сервер — Node.js, HTTPS API и WebSocket для событий, PostgreSQL для учётных записей, шифротекста и синхронизации, закрытое хранилище для зашифрованных фото. LiveKit SFU пересылает зашифрованные медиадорожки, TURN обеспечивает подключение из сетей, где прямой путь недоступен. Это кандидаты на реализацию после проверки совместимости.

Ключевые сущности — участник, приглашение, устройство, членство, чат, сообщение, вложение, позиция прочтения, вызов и медиасессия. Сообщение получает стабильный ID и позицию в чате. Повторы отправки идемпотентны. После восстановления связи клиент запрашивает пропущенные события по курсору. Прочтение в общих чатах синхронизируется только между устройствами владельца позиции. В личке второй участник получает сквозно зашифрованное подтверждение прочтения.

## Структура репозитория

Проект использует один репозиторий с npm workspaces. Границы девяти модулей и критерии готовности описаны в [TASKS.md](TASKS.md).

```text
ZVONOCHEG/
├── docs/
│   ├── README.md
│   ├── DESIGN.md
│   ├── ROADMAP.md
│   └── TASKS.md
├── package.json                 # npm workspaces и команды проекта
├── package-lock.json
├── apps/
│   ├── web/                     # Браузерная сборка общего интерфейса
│   ├── api/
│   │   ├── src/
│   │   │   ├── accounts/        # Приглашения, сессии и роли
│   │   │   ├── chats/           # Сообщения, события и синхронизация
│   │   │   ├── attachments/     # Доступ к зашифрованным объектам
│   │   │   ├── media/           # Комнаты и токены LiveKit
│   │   │   └── calls/           # Состояния и события вызовов
│   │   └── migrations/          # Схема PostgreSQL
│   └── windows/                 # Electron, IPC, захват и обновления
├── packages/
│   ├── client/                  # Общий React-интерфейс и клиентская логика
│   ├── crypto/                  # E2EE, ключи и восстановление истории
│   └── protocol/                # Схемы запросов, ответов и событий
├── infra/
│   ├── local/                   # Локальные сервисы и тестовые данные
│   └── deploy/                  # VPS, TLS, LiveKit/TURN и бэкапы
└── tests/
    ├── e2e/                     # Сценарии веб ↔ веб и веб ↔ Windows
    └── load/                    # Нагрузочные сценарии Z13
```

Веб- и Windows-клиенты используют интерфейс из `packages/client`. Electron предоставляет системные уведомления и захват через ограниченный IPC. Работа с ключами и расшифровка выполняются на клиенте через `packages/crypto`. API проверяет права, хранит и выдаёт шифротекст и управляет состояниями чатов, комнат и звонков.

На Z01 добавляются npm workspaces, `apps/web`, `apps/api`, `packages/client` и `infra/local`. На Z02 появляется `packages/crypto`, на Z03 начинается интеграция медиа, на Z09 добавляется `apps/windows`. `packages/protocol` появляется вместе с первым общим контрактом клиента и API. Остальные каталоги добавляются вместе с использующим их кодом.

## Модель безопасности и ключей

- Текст, фото, голос, камера и демонстрация шифруются на клиенте. Сервер маршрутизирует данные и видит служебные метаданные, включая членство, время, размеры и факт вызова. Админ приложения не получает ключи за счёт роли. Как участник общего чата он читает сообщения на общих основаниях.
- Прототип ключей — OPAQUE по RFC 9807 для входа без передачи пароля серверу. Из клиентского export key библиотечным KDF с отдельным контекстом выводится ключ обёртки для зашифрованного хранилища ключей аккаунта. Клиент распаковывает историю локально. Пароль должен выдерживать офлайн-подбор при краже серверного состояния. Смена пароля требует переобёртки и проверки восстановления. Сброс без старого пароля или доступных ключей даёт новый криптографический профиль и недоступность старой истории. Самостоятельный сброс и отдельный ключ восстановления отложены.
- Выбрать проверенную библиотеку группового протокола на этапе прототипа. Кандидат — MLS с аутентифицированными ключами устройств. Проверить, как новый клиент получает архив разрешённых исторических ключей из зашифрованного хранилища, включая сообщения, полученные с выключенными устройствами. Нужна проверка целостности каталога ключей и предупреждение о неожиданной смене идентичности. Простая выдача сервером произвольного ключа по имени неприемлема. Синхронизация исторических ключей сохраняет риск раскрытия архива при компрометации ключа аккаунта.
- Для фото шифровать содержимое и миниатюру на клиенте. Ссылки на скачивание ограничить по времени и правам. Серверу не нужны ключи для выдачи зашифрованных объектов.
- Для медиа проверить клиентский обмен ключами и обновление ключа при смене состава участников или отзыве доступа. SFU получает токен подключения, ключ остаётся у участников. При ошибке ключей останавливается публикация и приём. Отзыв доступа ограничивает будущие сообщения и звонки, уже полученные копии остаются у получателей.
- Веб-клиент доверяет доставленной сборке. Оператор, способный подменить JavaScript, может внедрить сбор паролей или ключей. Разделить публикацию веб-сборки и серверные доступы, ограничить источники скриптов, исключить сторонние скрипты. Для Windows использовать подписанный установщик и проверяемые обновления. Проверять TLS, разграничение доступа, отсутствие открытого содержимого и ключей в БД, резервных копиях и логах.

## Звонки и демонстрация

Личный вызов имеет серверный ID и состояния «вызов», «принят», «отклонён», «отменён», «пропущен», «завершён». Первое принятие фиксируется атомарно для всех устройств. Открытый свёрнутый Windows-клиент показывает уведомление и звонит. В открытой фоновой веб-вкладке звонок зависит от разрешения уведомлений, политики звука и состояния вкладки. Клиент предлагает включить уведомления и проверить звук заранее. После закрытия клиента вызов не звонит, запись появляется в чате после синхронизации. Истечение вызова и разрыв связи дают одну запись без дублей.

Для всего экрана публикуется только видеодорожка демонстрации. Для приложения захватывается звук выбранного источника. В Windows проверить захват аудио дерева процесса через Application Loopback и передачу дорожки в E2EE. Веб начинает с проверенных режимов Chromium, включая звук вкладки. Если изолированный звук выбранного окна недоступен, интерфейс явно показывает «без звука» и предлагает Windows-клиент. Общий системный звук не подмешивается. Микрофон — отдельная дорожка.

## Эксплуатация

Постоянный Linux VPS в российском дата-центре с публичным IP, доменом и TLS. На старте один хост для API, БД и медиастека при подтверждении тестом, резервные копии отдельно. Разрешить необходимые порты медиа и TURN, проверить UDP и путь через TURN/TLS из домашних сетей друзей. Для тарифа учитывать CPU, исходящую полосу и стоимость трафика. Один VPS создаёт общую точку отказа. Отслеживать доступность, CPU, сеть, потери, задержку и заполнение диска без записи содержимого переписки.

Обычная нагрузка — 10 человек в одной голосовой комнате и одна демонстрация. Пик — 20 с тем же сценарием. Число одновременных камер ещё не согласовано. В тестах начать с двух камер отдельно от основного профиля и измерить предел. Выбрать хостинг после измерений и проверки доступности из сетей участников.
